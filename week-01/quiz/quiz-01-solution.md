## 문제 1: [이론] 상태 머신 (객관식)

이더리움에서 "상태 전이가 원자적(atomic)이다"라는 말의 의미를 가장 잘 설명한 것은?

다음 상황을 고려하세요:

```
Alice가 Bob에게 1 ETH를 보내는 트랜잭션을 실행합니다.
중간에 가스가 부족해져서 트랜잭션이 실패했습니다.
```

**보기:**
A) Alice의 잔액만 감소하고 Bob의 잔액은 변하지 않는다
B) Alice의 잔액과 Bob의 잔액 모두 변하지 않고, 가스비만 소모된다
C) 네트워크가 자동으로 부족한 가스를 보충해서 트랜잭션을 완료한다
D) 트랜잭션이 절반만 실행되어 0.5 ETH만 전송된다

**답변:**
정답: B
원자적(atomic)이라는 것은 처리 단위가 '전부 처리되거나(All) 아예 처리되지 않거나(Nothing)' 둘 중 하나라는 것을 의미합니다. 트랜잭션 실행 중 가스 부족 등의 이유로 실패하면, 상태 전이가 완료되지 못하고 실행 이전 상태로 롤백됩니다. 단, 처리 과정에서 소모된 연산 비용인 가스비는 채굴자/검증자에게 지급되므로 소모됩니다.

## 문제 2: [이론] 결정론적 실행 (객관식)

이더리움 EVM이 "결정론적(deterministic)"으로 실행된다는 것의 핵심 이유는 무엇인가요?

**보기:**
A) 모든 노드가 같은 하드웨어를 사용해야 해서
B) 같은 입력(트랜잭션)이 주어지면 모든 노드가 같은 결과(상태)를 도출해야 하므로
C) 중앙 서버가 모든 계산을 수행하고 결과를 배포해서
D) 트랜잭션이 항상 1초 안에 처리되어야 해서

**답변:**
정답: B
블록체인은 수많은 탈중앙화된 노드들이 동일한 원장(상태)를 유지해야 하는 시스템입니다. 노드마다 다른 결과가 나온다면 서로 합의(Consensus)를 이룰 수 없고 네트워크가 분기(Fork)되는 치명적인 문제가 생깁니다. 따라서 같은 트랜잭션을 입력했을 때 어떤 환경에서든 반드시 동일한 결과를 도출해야 합니다.

## 문제 3: [이론] EOA vs CA (객관식)

다음 중 EOA(Externally Owned Account)와 CA(Contract Account)의 차이를 올바르게 설명한 것은?

**보기:**
A) EOA는 코드를 실행할 수 있고, CA는 코드를 실행할 수 없다
B) EOA만 트랜잭션을 시작할 수 있고, CA는 EOA에 의해 호출될 때만 실행된다
C) CA만 ETH를 보유할 수 있고, EOA는 ETH를 보유할 수 없다
D) EOA와 CA는 동일한 기능을 가지며 이름만 다르다

**답변:**
정답: B
트랜잭션을 시작하려면 개인키(Private Key)를 사용해 디지털 서명(Signature)을 생성해야 합니다. EOA는 사용자가 개인키를 보유하고 있지만, CA는 배포된 코드(스마트 컨트랙트)일 뿐 자체적인 개인키가 없습니다. 따라서 CA는 스스로 트랜잭션을 발생시킬 수 없으며, EOA나 다른 CA에서 트랜잭션을 수신해야만 그 내부 로직을 실행할 수 있습니다.

## 문제 4: [이론] 계정 상태 필드 (객관식)

이더리움 계정 상태의 4가지 필드 중 `nonce`의 역할을 올바르게 설명한 것은?

다음 상황을 고려하세요:

```
Alice의 현재 nonce: 5
Alice가 두 개의 트랜잭션을 동시에 전송합니다:
- TX-A: nonce=5, Bob에게 1 ETH 전송
- TX-B: nonce=5, Charlie에게 2 ETH 전송
```

**보기:**
A) 두 트랜잭션 모두 성공적으로 처리된다
B) TX-A만 처리되고 TX-B는 무시된다 (또는 그 반대)
C) 두 트랜잭션 모두 실패하고 Alice의 자산이 동결된다
D) 네트워크가 자동으로 TX-B의 nonce를 6으로 변경한다

**답변:**
정답: B
트랜잭션에 포함되는 `nonce`는 계정이 성공적으로 전송한 총 트랜잭션 개수를 의미합니다. 이는 하나의 트랜잭션이 단 한 번만 실행됨을 보장하는 역할을 합니다. 네트워크에는 nonce 5인 트랜잭션이 한 번 성공적으로 처리된 후 해당 계정의 nonce가 6으로 업데이트됩니다. 동일한 nonce 5를 가지고 있는 다른 하나는 이미 사용된 nonce로 간주되어 거부(무시)됩니다. (재전송 공격 취약성을 방어함)

## 문제 5: [이론] World State (객관식)

World State에 대한 설명 중 올바른 것은?

**보기:**
A) World State는 최신 100개 블록의 트랜잭션만 저장한다
B) World State는 모든 계정의 현재 상태(주소 -> 상태 매핑)를 나타낸다
C) World State는 EOA의 정보만 저장하고 CA 정보는 별도로 관리한다
D) World State는 각 노드마다 다른 값을 가질 수 있다

**답변:**
정답: B
World State는 이더리움 시스템 전체의 글로벌 상태를 의미합니다. 모든 이더리움 주소를 키(Key)로 하고, 해당 계정의 상태 객체(Account State: nonce, balance, storageRoot, codeHash)를 값(Value)으로 가지는 거대한 키-값 매핑 자료구조입니다. 전화번호부에서 이름을 찾으면 전화번호를 알 수 있듯, 주소를 통해 현재 보유 잔액이나 배포된 코드 등을 알 수 있기 때문에 구조가 비슷합니다.

## 문제 6: [이론] 상태 변수 vs 지역 변수 (단답형)

Solidity에서 `상태 변수(state variable)`와 `지역 변수(local variable)`의 차이는 무엇인가요?

다음 코드를 보고 설명하세요:

```solidity
contract Example {
    uint256 public count;  // 이것은 무엇인가요?

    function calculate(uint256 input) public pure returns (uint256) {
        uint256 result = input * 2;  // 이것은 무엇인가요?
        return result;
    }
}
```

**답변:**
1. `count` (상태 변수):
- 위치: 블록체인 영구 저장소인 Storage에 저장
- 지속성: 트랜잭션 종료 및 블록 생성이 완료된 이후에도 블록체인 네트워크 상에 데이터가 영구히 보존됩니다.
- 비용: 블록체인 상에 데이터를 기록하므로 가스 비용이 가장 비쌉니다.

2. `result` (지역 변수):
- 위치: 실행 중에만 사용하는 임시 메모리인 Memory(로컬 스택) 할당
- 지속성: 함수 실행이 끝나면 즉시 휘발되며 보존되지 않습니다.
- 비용: 임시로만 쓰고 버리는 공백이므로 상태 변수보다 가스 비용이 훨씬 저렴합니다.

## 문제 7: [이론] 원자성의 이유 (단답형)

이더리움에서 트랜잭션이 "원자적(atomic)"으로 처리되어야 하는 이유는 무엇인가요?

**왜** 부분적으로 성공하는 트랜잭션을 허용하면 문제가 될까요? 구체적인 예시와 함께 설명하세요.

**답변:**
트랜잭션 실행 중 부분적인 데이터 변경이 허용되면, 블록체인 전체 상태 무결성이 무너지기 때문입니다.
예를 들어 A계좌에서 B계좌로 ETH를 전송할 때 송금 트랜잭션이 절반만 진행되었다고 가정한다면, A계좌에서는 출금되어 잔액이 줄어들었는데 B계좌에는 입금 처리가 안 된 채로 트랜잭션이 끝나버리는(돈이 증발하는) 치명적인 데이터 불일치 상태에 빠질 수 있습니다.

## 문제 8: [이론] 계정 구조 설명 (단답형)

EOA에는 `codeHash`와 `storageRoot`가 왜 의미가 없나요?

**답변:**
EOA(외부 소유 계정)는 일반 사용자가 개인키로 통제하는 단순 잔여물 보유 계정입니다.
CA(컨트랙트 계정)와 다르게 실행할 수 있는 스스로 작성된 스마트 컨트랙트 코드(`codeHash`)가 없으며, 영구적으로 상태를 저장하고 보관할 공간(`storageRoot`)도 구성상 필요하지 않기 때문에 항상 비어있는 값으로 존재합니다.

## 문제 9: [코드] Counter 읽기 (코드 읽기)

다음 Counter.sol 코드를 분석하세요:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.26;

contract Counter {
    uint256 public count;

    function getCount() public view returns (uint256) {
        return count;
    }

    function increment() public {
        count += 1;
    }

    function decrement() public {
        require(count > 0, "Count cannot go below zero");
        count -= 1;
    }
}
```

**1) `public` 키워드의 역할:**
`count` 변수에 `public`이 붙으면 어떤 일이 자동으로 일어나나요?

**답변:**
Solidity 컴파일러가 해당 상태 변수의 값을 자동으로 외부에서 읽어올 수 있도록, 동일한 이름을 가진 `count()`라는 Getter 함수(조회 전용 함수)를 암묵적으로 자동 생성해줍니다.

**2) `view` 키워드의 의미:**
`getCount()` 함수에 `view`가 붙은 이유는 무엇인가요? `view`를 제거하면 어떻게 될까요?

**답변:**
`view`는 해당 함수가 블록체인의 어떠한 상태도 변경하지 않고, 오직 상태를 '읽기'만 한다는 것을 보장하는 키워드입니다. 이렇게 읽기 전용 함수로 호출하면 가스 비용을 아낄 수 있습니다. 만약 `view` 키워드를 제거하게 되면 이더리움은 관례상 상태를 변경하는 쓰기 트랜잭션 대상 함수로 간주하여 가스를 소모하게 됩니다.

## 문제 10: [코드] Counter 동작 예측 (코드 읽기)

위의 Counter 컨트랙트에서 다음 시나리오를 분석하세요:

**시나리오:**
```
초기 상태: count = 0

1. increment() 호출
2. increment() 호출
3. decrement() 호출
4. decrement() 호출
5. decrement() 호출
```

**질문 1:** 5번째 `decrement()` 호출의 결과는 무엇인가요?

**답변:**
호출이 실패하면서 지정된 에러메세지를 던지며 트랜잭션이 Revert(무효화)됩니다. 4번째 호출까지 `count` 값은 정확히 0으로 떨어진 상황이라 `require(count > 0)` 조건을 충족하지 못하기 때문입니다.

**질문 2:** 왜 `decrement()` 함수에 `require(count > 0, ...)` 조건이 필요한가요?

**답변:**
`uint256` 자료형은 양수와 0만 표현할 수 있는 부호 없는 정수입니다. `count`가 0일 때 1을 빼려고 시도하면 음수로 넘어가는 Underflow(언더플로우)가 발생합니다. (Solidity 0.8 버전부터는 이 연산 자체를 기본적으로 잡아내어서 revert 시켜주기는 합니다). 이 과정에서 `require`를 통해 명시적인 에러 메시지를 뿜어내며 안전하게 함수를 튕겨내기 위해 필요합니다.
